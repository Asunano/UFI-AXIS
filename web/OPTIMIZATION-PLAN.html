二、发现与建议（按优先级）

P0 · Naive UI 改为按需引入

高收益
证据：src/main.ts:3,12 使用 import naive from 'naive-ui' + app.use(naive) 全局注册；无组件级 import { NXxx } from 'naive-ui' 注册。产物 naive-ui-*.js 达 1.36 MB / gzip 362 KB，且为 entry 依赖，首屏必载。
影响：首屏 JS 的 ~80% 是 naive-ui；登录页等轻量页也要等它解析完才渲染，拖慢 FCP/LCP。
建议方案（不改代码，仅方向）：
  • 引入 unplugin-vue-components + unplugin-auto-import，配置 NaiveUiResolver，删除 main.ts 的 app.use(naive)。
  • 组件改为按使用自动注入；样式由插件按需引入，无需手动 import 'naive-ui/...'。
  • 主题（darkTheme / zhCN）已在 App.vue 局部引入，不受影响。
预估收益：首屏 naive-ui 子集（仅首屏所用组件）可降至约 120–160 KB gzip；整体首屏 JS 预计 下降 40–45%。后续路由所需组件随导航按需加载。
状态：✅ 已于 2026-09-04 完成。web/vite.config.ts 接入 unplugin-vue-components + NaiveUiResolver，src/main.ts 删除 app.use(naive)；并移除 manualChunks 中强制的 naive-ui 整块，使各组件随路由按需分片。
实测：naive-ui-*.js 整库（原始 1.36 MB / gzip 362 KB，原强制首屏）已消失；首屏静态 JS 仅 index(gzip 73 KB) + vendor(60 KB) ≈ 133 KB gzip，naive 各组件（Select/Tabs/Input/FormItem 等）按视图懒加载。降幅远超 40–45% 预估。vue-tsc -b 零报错，生成的 src/components.d.ts 已提交。
偏差说明：未引入 unplugin-auto-import —— 因仓库已对每个 naive 组合式 API（useMessage/useDialog/...）显式 import，再加 auto-import 会与既有显式导入冲突导致重复声明；仅组件按需即可达成目标，组合式 API 本身已是按需。

P0 · 延迟加载设备签名 crypto（@noble/curves）

高收益
证据：src/composables/useApi.ts:5 静态 import { signRequest, toSignableUri } from '@/composables/deviceIdentity'；而 deviceIdentity.ts:44-45 引入 @noble/curves/p256 + @noble/hashes/sha256。该模块被 useApi（首屏共享 chunk）静态拉入。
影响：crypto 库在登录前、甚至未配对时就被下载解析，但签名仅用于已登录请求与 WebSocket 握手，属于“用到才需要”。
建议方案：
  • 将 deviceIdentity 在 useApi.ts 中改为动态 import()（在请求拦截器首次需要时 await 加载并缓存），使 crypto 脱离首屏 chunk。
  • WebSocket 握手（stores/websocket.ts）同理改为懒加载，与登录时序对齐。
预估收益：首屏减少 ~6–10 KB gzip，并减少主线程解析开销；crypto 包归入“登录后”路径。
实测（2026-09-04）：已落地。新增 src/composables/deviceIdentityLazy.ts（缓存式动态 import()，全程只加载一次 crypto）；useApi.ts 请求拦截器、stores/websocket.ts 握手、FilesView / LoginView / SpeedTestModal 三处调用点全部改为按需加载。产物已验证：@noble/curves / @noble/hashes 完全隔离进独立 deviceIdentity-*.js chunk（原始 46.9 KB），不在首屏 index/vendor 预载列表（index.html 仅预载 index+vendor+css），grep 确认 entry/vendor chunk 无 @noble 标记。vue-tsc -b 零报错。

P1 · 拆分 4 个巨型视图，启用子分片

可维护 + 分片
证据：行数 —— NetworkView.vue 2024、DashboardView.vue 1838、TasksView.vue 1620、DeviceView.vue 1292。既有 REFACTOR-PLAN 只覆盖 sms/files/alerts/terminal，未触及这四个。
影响：① 单文件审查/diff 成本高、回归风险大；② 整视图作为一个 chunk 无法再细分子模块；③ 含图表/表格的重段与首屏其余逻辑耦合，无法按需懒加载。
建议方案：
  • 按 GridCard 边界把每个巨型视图拆成 components/<View>/XxxCard.vue 子组件（沿用仓库已有的 GridCard / InfoRow / ValueBadge 公共件）。
  • 对重渲染子段（如 Dashboard 的图表区、Network 的流量表）用 defineAsyncComponent 进一步懒加载，配合 <Suspense>。
  • 状态上提：把各卡共享的 store 数据保留在 stores/*（已有 dashboard.ts 等），子组件只接收 props / 读 store。
预估收益：单文件降至 300–600 行量级；首屏进入某视图时仅加载该视图所需子块；回归面收窄。

P1 · 轮询统一 + 标签页隐藏即暂停

运行时纪律
证据：composables/useRealtime.ts 已被 12 个视图采用（含请求堆积保护），工程良好；但 stores/service.ts:82 仍用裸 setInterval 无该保护，且与 useRealtime 行为不一致。全局未见 document.visibilityState 暂停逻辑。
影响：后台标签页持续轮询浪费带宽与设备 CPU；service store 的裸定时器与其他视图行为不一致，易遗漏。
建议方案：
  • 将 stores/service.ts 的轮询收敛进 useRealtime（或复用同一 guard 模式）。
  • 在 useRealtime 内监听 visibilitychange：隐藏时 clearInterval、可见时重启，减少无谓请求。
预估收益：多开/后台场景请求量显著下降；定时器行为一致、无泄漏。

P1 · 增加请求取消（AbortController）

健壮性
证据：全仓 grep AbortController/CancelToken/signal 仅命中 contract.ts 的字段名 SIGNAL，无任何实际取消逻辑。轮询/切换路由时旧请求仍可能落地。
影响：快速切换路由或轮询重叠时，迟到响应可能写入已卸载组件（Vue 警告）或覆盖新数据；浪费带宽。
建议方案：在 useApi 的 axios 实例中为每个请求挂 AbortController；useRealtime 每轮 tick 复用/重置 controller，组件卸载或新一轮开始时 abort() 上一轮。
预估收益：消除卸载后 setState 告警、降低竞态覆盖概率、节省后台请求。
实测（2026-09-04）：已落地，范围扩到「请求取消 + 轮询暂停」两者。新增 useRequestScope.ts（组件级 AbortController 集合，onUnmounted 时统一 abort）+ useCancellableApi.ts（在 useApi 单例之上包装：每次请求注入受作用域跟踪的 signal，取消时 resolve 为 {__canceled:true} 而非抛错，调用方 if(data) 自然跳过、不弹错误）。14 个轮询视图（Dashboard/Monitor/Network/AlertList/Tunnel/Tasks/Sms/Downloads/Device 四 Tab/Logs/Update）的 getApiClient() 改为 useCancellableApi()。useRealtime.useInterval 新增全局 visibilitychange 暂停：浏览器标签页隐藏时停全部活跃轮询、回到前台恢复（仅恢复隐藏前活跃者，手动 stop 不受影响）。vue-tsc -b 零报错，构建无回归（useCancellableApi 独立 ~1KB chunk）。

P2 · 交付层启用 Brotli / Gzip

交付优化
证据：dist/ 仅产出未压缩 .js/.css；core 托管静态文件，且 vite.config.ts 未配置压缩插件。
影响：naive-ui 362 KB gzip 在传输层若再经 Brotli 可再降 ~15–20%；当前未预生成压缩产物。
建议方案：二选一 —— ① vite-plugin-compression 预生成 .br/.gz 并由 core 按 Accept-Encoding 回送；② 直接在 core（Ktor）静态路由开启 Brotli/Gzip。优先方案①（构建期完成，零运行时成本）。
预估收益：传输体积再降 15–20%，尤其利好弱网卡设备首次进入。
状态：✅ 已于 2026-09-04 完成（最终采用方案② 运行时压缩）。在 core/network 的 HttpServer.configurePlugins() 安装 Ktor Compression 插件，对 JS / CSS / JSON / SVG / HTML / woff2 启用 gzip（priority 1.0）与 deflate（priority 0.5），minimumSize(1024) 跳过极小文件；对单用户本地管理面板足够，且零构建期成本、零 assets/ZIP 契约改动、不动 WebResourceManager。依赖修正：原 libs.versions.toml 的 ktor-server-content-encoding 在 2.3.12 不存在（已查 Maven Central 返回 404），已改为正确的 ktor-server-compression（2.3.12 已验证存在）。
实测待办（需本机）：沙箱无 Android SDK 无法编译。请在本机执行 ./gradlew :app:assembleDebug 验证编译；用 curl -sI -H "Accept-Encoding: gzip" http://<设备IP>:8088/assets/<任意hash>.js 确认响应头出现 Content-Encoding: gzip 且 Content-Length 明显小于原始大小。若需比 gzip 再降 ~15–20%，可后续叠加「构建期 .br 预生成 + core 协商」，但会引入 assets/ZIP 契约变更，当前非必需。

P2 · 收紧 TypeScript / 清理 any

质量
证据：tsconfig.json 已开 strict + noUnusedLocals + isolatedModules（良好）；但 stores/dashboard.ts 的 5 个实时字段用 Record<string, any>、stores/service.ts 用 catch (e: any) 读 e?.response?.data?.error，且未启用 verbatimModuleSyntax。
建议方案：启用 verbatimModuleSyntax；将实时数据 store 的 any 收敛为显式接口（core 字段已在 contract.ts 定义，可直接复用）；把 echarts option 用 markRaw/shallowRef 包裹（dashboard store 已用 shallowRef，保持）。
预估收益：编译期更早暴露字段错位；为未来升级 vue-tsc 铺路。
状态：✅ 已于 2026-09-04 完成。web/tsconfig.json 启用 verbatimModuleSyntax: true——全仓 vue-tsc -b 零报错（代码已普遍使用 import type，无违规引入）；stores/dashboard.ts 的 5 个实时字段（signal/cpu/traffic/battery/memory）由 Record<string, any> 收敛为 SignalInfo / CpuInfo / TrafficRealtime / BatteryInfo / 新增 MemoryInfo 显式接口（初始值改 null，并补 ?. 安全访问：NetDetailChartCard.vue 两处 trafficData.tx/rx_speed、DeviceTopBar.vue 的 realtimeSignal || {}）；stores/service.ts 三处 catch (e: any) 改为 catch (e) + composables/utils.ts 新增 toApiErrorMessage(e, fallback) 按 axios 信封收窄 unknown。npm run build 零报错、产物 crypto 隔离未回归。

四、建议实施顺序

  1. 接入按需引入插件（unplugin 双件 + NaiveUiResolver），删除全局 app.use(naive)；npm run build 验证产物与首屏体积。— 单项收益最大。
  2. crypto 动态化：useApi / websocket 中把 deviceIdentity 改为懒加载 import。单独提交。
  3. 请求取消 + 轮询一致性：在 useRealtime 补 AbortController 与 visibilitychange 暂停；收敛 stores/service.ts 裸定时器。
  4. 巨型视图拆分：优先 NetworkView / DashboardView，按 GridCard 边界拆子组件，重段 defineAsyncComponent 懒加载。（与 REFACTOR-PLAN 的 sms/files/alerts/terminal 互不冲突，可并行）
  5. 交付压缩：接入 vite-plugin-compression 预生成 .br，core 静态路由回送。—— 已改为 Ktor 运行时 Compression 插件（gzip/deflate），见上方 P2 实测，免 assets/ZIP 契约改动。
  6. TS 收紧：启用 verbatimModuleSyntax，清理实时数据 any。

五、风险与注意

  • Naive UI 按需引入的坑：部分组件依赖全局样式/指令（如 NMessageProvider 的 useMessage 需在 Provider 内）。仓库已用 useMessage() 调用，需确认调用方处于对应 Provider 子树，否则改按需后运行期报“No outer …”。建议先用单视图灰度。
  • 不改 API 契约：以上优化均不触碰 core 接口路径/字段；仅 crypto 加载时序与交付压缩涉及 core 静态托管配置（第 5 步）。
  • 验证基线：每步以 cd web && npm run build 零报错为门槛，并用 DevTools Network 核对首屏 chunk 与轮询暂停行为。
